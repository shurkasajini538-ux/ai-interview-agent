# 面试工坊技术设计

## 架构

浏览器前端（HTML/CSS/JavaScript）通过本机 JSON API 访问 Python ThreadingHTTPServer。Python 负责文档解析、本地 OCR、模型调用和 SQLite 存储。运行不依赖云端网页托管、Node 服务或 CDN。

## 数据链路

1. 文件限制与格式检查 → 本地提取文字 → 简历原文及结构保存。
2. 固定简历快照 + 岗位描述 + 历史薄弱点 → 生成结构化题目。
3. 初次回答 → 一次针对性追问 → 补充回答或直接评分。
4. 模型四项评分经过范围、维度完整性与引用校验，总分由服务端计算。
5. STAR 接受的事实片段必须是用户回答的连续原文；不符合的片段被丢弃并使用明确占位。
6. 本题重答保留旧尝试；完成后导出报告与完整记录。

## 状态

题目：`initial → followup → evaluated`。也可 `followup → evaluated`（不补充）、`initial / followup → skipped`，以及 `evaluated → initial`（保留历史后重答）。本轮由 `active → completed`。

服务端核对当前题目的稳定 ID；题目不会因提交回答而重新生成。模型调用异常回退时保留原题目与回答，并在反馈中标记。

## 持久化与并发

- SQLite 使用 WAL，每次操作独立连接，事务结束后关闭。
- 记录按随机浏览器身份隔离；本机 Cookie 为 HttpOnly、SameSite=Strict。
- 每轮练习有并发锁。回答和请求去重记录在同一事务保存。
- 简历编辑不修改已有练习快照。报告包含引擎、时间、分项依据和历次重答。
- API Key 使用 Windows DPAPI，配置仅向前端返回“是否已配置”。

## 使用范围

仅监听本机地址；来源检查、防路径遍历、输入大小限制和前端转义用于减少本机网页应用常见风险。浏览器身份不是面向互联网的账号认证，因此本应用不开放远程多人访问。

OCR 是按需初始化的 CPU 推理，最多两个推理线程。PDF 最多 30 页，扫描页最多 6 页。模型请求有超时，不将服务端错误原文或凭证回传前端。
